# Troy Correct — 從結構根治重複犯錯

當 AI 或團隊在同一個專案裡**反覆犯同一類錯（≥ 2 次）**，不再只是口頭提醒或往規範文件多塞幾行字，而是把錯徹底擋在編譯、Lint 或架構邊界之外。

> 若存在 `~/.agents/CONTEXT.md`，先讀取並遵守其語言與安全規範。若專案另有歸檔復盤流程（例如歸檔時的踩坑檢查），`troy-correct` 負責深入實作出跨模組的長期防線。

## 核心設計前提

把每個接手這包程式的人／AI 都假設成：**「只看手邊打開的 1~2 個檔案、會抄旁邊最近的舊寫法、走最短能通過編譯的路」**。  
因此防呆的目標不是「要求讀者乖乖記住」，而是**讓看起來最順手的那條路剛好就是唯一正確的路**。

## 防呆強度階梯（由高到低，能用上層就不用下層）

1. **L1｜架構消除**：單一狀態來源、把內部細節封進模組（hide internals）讓錯誤 import 直接報錯、刪掉容易被誤抄的過時範例或死碼。
2. **L2｜型別攔截**：用更嚴謹的 TypeScript 型別（如 discriminated union、branded type、readonly／必傳欄位）讓錯誤狀態在編譯階段就寫不出來。
3. **L3｜Lint 或自動化檢查腳本**：型別攔不住的語意規則，寫成 ESLint / 靜態檢查腳本，且**錯誤訊息要直接寫出「請改用哪個檔案／型別／函式」**（若舊程式累積太多違規，採增量門檻只擋新增異動）。
4. **L4｜行為測試**：補上鎖定行為的測試（確保壞掉必紅燈，但不綁死內部實作細節）。
5. **L5｜文件或 Agent 規則（最後手段）**：僅保留真正需要工程判斷、無法機械化的原則；**一旦某條規則已升級到 L1–L4 自動檢查，就從文件刪掉以減少文字雜訊**。

## 執行流程

### Step 1：盤點並歸類重複錯誤
1. 檢視來源（唯讀）：近期 `git log` 中的 `fix:` / `revert:` commit、Review 問題紀錄、專案內的規範文件、程式碼中標記 workaround 的註解，以及使用者本次指出的糾正。
2. 將問題合併歸類：**同一類錯必須實際出現至少 2 次才成案**（單次失誤不急著過度設計）。

### Step 2：對照防呆階梯提出方案（先確認再動手）
列出清單給使用者挑選要處理哪幾類，每類包含：
- **錯誤類別名稱**（出現幾次、真實範例位置 `file:line` 或 commit）
- **建議防呆層級與具體改法**（優先找 L1–L3，說明為何不需停留在 L5）
- **預期影響檔案範圍**

> **原則：未經使用者選取確認，不擅自修改 ESLint、TypeScript 設定或重構專案架構。**

### Step 3：逐類實作並完成「紅燈反證」
針對使用者拍板的類別，**一類一個獨立工作單元**依序處理：
1. 套用選定層級的結構／型別／Lint／測試修補，並修正被新檢查掃出來的現行違規（若與本次範圍無關的大量舊債，明列例外或採 diff gate）。
2. **紅燈反證（強制驗證）**：實際拿「過去真的出過錯的那段程式碼（或最小重現片段）」套進來跑檢查，**親眼看到新防線確實報錯／紅燈攔下並印出清楚修正提示**，隨後還原測試片段並確認全體檢查恢復綠燈。
3. 若為該類錯寫了 L5 例外豁免註解（例如 eslint-disable），必須附帶原因與失效／檢視條件。

## 回報格式

1. **錯誤盤點與候選清單**（Step 2 確認前先停在這步）
2. **已完成防呆紀錄**（確認實作後回報）：
   - 處理類別與採用層級（L1–L5）
   - 修改檔案清單與新規則觸發的檢查指令
   - **紅燈反證輸出**：貼上「放進歷史錯誤片段時被攔截」的真實失敗輸出，以及復原後全綠結果
   - 若因此淘汰了多餘的文字規範，列出建議精簡移除的舊規則條目。
