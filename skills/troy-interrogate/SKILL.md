# Troy Interrogate — 對抗式實跑找碴

不靠人工或 AI 用眼睛猜 Bug，而是**派找碴 subagent 真的寫小測試或 repro 腳本把剛改好的程式碼弄壞**。只報有實際跑出失敗畫面的問題，不改動主工作區任何檔案。

> 若存在 `~/.agents/CONTEXT.md`，先讀取並遵守其語言與安全規範。若已安裝 `troy-blast-radius`，可藉此釐清高風險表面，否則獨立執行即可。

## 安全與隔離紅線（絕不違反）

- **不動主工作區**：所有找碴、修改與執行都必須在獨立的臨時 `git worktree` 內進行，主目錄只保持唯讀檢查與最後重跑驗證。
- **嚴禁讀取或外洩 `.env*`／金鑰檔**：所有 repro 與測試只允許使用專案既有的隔離測試環境、in-memory stub 或本地 mock。
- **嚴禁觸碰非測試環境與真實外部服務**：禁止連線開發／正式資料庫、Redis，或發出真實金流、簡訊、Email 請求。

## 執行流程

### Step 1：鎖定範圍與意圖（Frame）
1. **確認檢查範圍**：若使用者已指定檔案、模組或 commit 範圍，以此為準；否則取目前分支相對 base branch 的改動（`git diff <merge-base>..HEAD` 加上工作區未提交異動）。若無任何可檢視改動，直接停止並回報。
2. **用自己的話重述意圖**：從使用者需求、commit 訊息或規格摘要出「這批改動預期達成什麼、有哪些絕對不能壞的規則」。若意圖完全不清楚，先向使用者確認再往下跑。

### Step 2：複製到臨時 worktree 並派對抗角色（Fan-out）
1. 建立 2~3 個隔離的臨時 `git worktree`（依當前工具支援方式建立，例如 `git worktree add` 搭配臨時路徑並同步工作區尚未提交的 patch；結束時必清除）。
2. 依本次改動風險大小與性質，**動態派 2~3 個對抗 subagent**（同一批次平行啟動），各自專攻不同攻擊面：
   - **視角 A｜業務邊界與異常輸入**：null／undefined、空陣列、0／負數／極大值、時區跨日、既有不變量是否被改動打破。
   - **視角 B｜信任邊界與權限／金額**（改動涉及金額、折扣、運費、認證授權時必開）：Client 是否可傳假欄位覆蓋後端計算、IDOR 越權、未授權存取。
   - **視角 C｜並發競爭與狀態機／回滾**（改動涉及寫入流程、交易、非同步任務或重試時必開）：重複請求冪等性、Race Condition、部分失敗未回滾。
3. **發給每個找碴 subagent 的一致指令（鐵律）**：
   - 只能針對「真的違反 Step 1 意圖」寫出可執行的 repro（失敗的單元測試、腳本或真實指令輸出）。
   - 每條回報必須附上：**標題、執行的完整指令、實際印出的錯誤輸出、以及意圖規定應有的正確結果**。
   - **嚴禁回報沒實際跑過的東西**——包括純風格建議、命名挑剔、「未來如果別人加了什麼可能會錯」的假設性警告。若真的找不到可重現錯誤，直接回報「無實證發現」即可。

### Step 3：主流程逐條重跑驗真（Prove or Drop）
1. 彙整各對抗 subagent 回傳的候選項目，**不直接照抄採信**。
2. 由主流程在乾淨的驗證位置逐條重跑對應指令／repro：
   - 確實能重現失敗，且該失敗真實違背 Step 1 意圖 → **保留**（相同根因合併成一條）。
   - 指令跑不動、其實只是環境設定缺漏、或根本沒違反原定意圖 → **剔除**（記錄剔除數量與原因）。
3. **清理臨時產物**：刪除所有為本次找碴建立的臨時 `git worktree` 與暫存 repro 檔案，確認主工作區 `git status` 與開始前完全一致。

## 回報格式

1. **改動意圖重述**：1~2 句說明本次假設必須守住的行為
2. **實跑確認的問題（Findings）**（若全部驗證都沒壞，直說「無實證發現」）：
   - **[#1 標題]**（發現來源視角）
   - 破壞了什麼意圖：一句話說明實際結果 vs 預期結果
   - 重現指令：`<exact command>`
   - 實跑失敗輸出摘要：`<observed output>`
3. **剔除紀錄（Dropped）**：列出剔除幾條候選與各自原因（例如：純推測無實跑、重複根因、不違背原定意圖），維持結果可稽核。
