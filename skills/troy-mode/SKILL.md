# Troy Mode — 個人 Playbook 總路由

在開始任何非瑣碎任務前，先讀取 `~/.agents/CONTEXT.md`（若存在）取得共用語言與對外表達原則，再用你自己的話用 1~2 句重述目標與最小可驗證完成標準，接著依下方路由表分派對應的 `troy-*` skill。

## `troy-*` 技能路由表

> 若使用者只單獨安裝部分 `troy-*` skill，目標 skill 不存在時直接依該列「核心產出」原則就地執行，不因缺少附屬 skill 而卡住。

| 任務意圖 | 呼叫 Skill | 核心產出 |
| :--- | :--- | :--- |
| 搞懂「這塊程式**怎麼運作**？邏輯該放哪一層？」 | `troy-how` | 唯讀追蹤呼叫鏈、模組邊界與 State Owner |
| 搞懂「**為什麼**當初這樣寫／這樣定規則？」 | `troy-why` | 查 `git log` / PR / 歷史文件，拆「事實 vs 推論 vs 空白」 |
| 評估「改這裡**會不會打壞別處**？」 | `troy-blast-radius` | 追 grep 看不到的隱性依賴並實跑證實關鍵假設 |
| 計畫／決策／規格還模糊，需要被**壓力測試盤問** | `troy-grilling` | 依設計樹逐輪逼出未定決策，未達共識不動工 |
| 需要外部一手來源**技術／產品調查筆記** | `troy-research` | 查證一手資料並輸出可追溯研究筆記 |
| **學觀念**（蘇格拉底反問）或 **Review 快速白話講懂** | `troy-teach-me` | 觀念採反問引導；Review 採漸進小圖 + 平行 `troy-how` / `troy-why` |
| 剛才 AI 的回答太難懂／跳步，要求**白話重講** | `troy-wait-what` | 唯讀重述上一段回覆，不擴張執行 |
| 驗證 skill／規範改動前後**實際行為差異** | `troy-eval` | 建立去識別化雙盲對照環境、平行實跑並交由匿名裁判評分 |
| 高風險改動寫完後，派找碴 AI **實跑把程式弄壞** | `troy-interrogate` | 建臨時 worktree 實跑 repro 驗證；只報真實失敗，不改主工作區 |
| 發現 AI／團隊**重複犯同一類錯（≥ 2 次）**，從根本堵洞 | `troy-correct` | 按架構→型別→Lint→測試階梯提案防呆，確認後實作並紅燈反證 |
| 替專案建立或改版更新**實機操作驗證腳本（`verify-*`）** | `troy-create-verify` | 讀懂專案啟動與操作面，產出／健檢 `verify-<app>` 與功能地圖 |
| 文件、PR 說明、README 或文章完稿後**去 AI 腔潤稿** | `troy-unslop` | 移除空洞形容詞、翻譯腔與 AI 句型，保留技術事實與台灣自然語感 |

## 通用執行紀律（所有路由共用）

1. **先理解再動手**：改陌生或跨模組程式碼前，優先跑 `troy-how`（結構）或 `troy-why`（脈絡），不在沒看懂合約前猜測修改。
2. **若專案內已有專屬工作流（例如專案內的 `AGENTS.md`、`.agents/skills/` 或團隊規範）**：`troy-mode` 負責個人分析／調查／審查前導；進入正式實作、修 Bug 或重構時，接回該專案既定的工作流與規範。
3. **證據優先（Prove It Works）**：不把「應該沒問題」、「能編譯」當完成；報告結論必附真實檔案行號、Commit 或實跑指令輸出。
4. **最小化決策打擾**：能自己從程式碼／紀錄查證的事實，不反問使用者；只把產品取捨或不可逆風險交給使用者拍板。
