# Troy Blast Radius — 變更爆炸半徑與安全實證

找出一個改動或 Diff 在「改動範圍之外」可能打壞什麼，並**用真實執行證據（而非紙上談兵）**證明關鍵假設到底安不安全。

> 搭配 `troy-how`（理解運作）與 `troy-why`（理解動機）使用：`troy-blast-radius` 專抓「靠 grep 找不到」的隱性破壞點。

## 核心原則：不信任自己寫得很好聽的分析

列出所有呼叫端只是基本動作（grep 一秒就做完），真正的價值是抓出**呼叫鏈之外的隱性耦合**，例如：
- 共用型別／DTO／OpenAPI／序列化欄位變化對下游（前後端、Worker、匯出報表）的影響
- DB Schema／Migration／CHECK Constraint／既有歷史資料或 Seed/Fixture 的相容性
- 非同步事件、排程、快取 Key、權限 Guard 順序或並發競爭（TOCTOU）
- 測試環境假資料、既有測試斷言或全域設定假設

## 執行流程

### Step 1：界定範圍與取得真實 Diff
- 若使用者指定某檔案／函式／分支，以此為準；否則檢視當前工作區與 base branch（例如 `git diff` / `git status`）的實際異動。

### Step 2：搜出 grep 看不到的隱性耦合
依本次改動觸及的層面，追查：
1. **資料與契約邊界**：有沒有跨模組／跨 repo（如前端、Admin、Worker、OpenAPI）消費這個輸出？有沒有字串拼接、反射、動態 key 或序列化依賴？
2. **狀態與時間軸假設**：有沒有依賴「某件事一定先發生」或「欄位一定非 null」的歷史資料／其他入口？
3. **錯誤與回滾路徑**：失敗時交易（Transaction）有回滾嗎？有沒有留下半套狀態或重複觸發副作用？

### Step 3：實際跑程式／檢查來驗證關鍵假設（Prove It Works）
挑出這次改動**安全成立最關鍵的 1~2 個事實**，盡可能往下走到最低層級的實證（並在報告寫清楚走到哪一層）：
1. ❌ 只靠嘴說（無價值，禁止）
2. ⚠️ 指到真實 `file:line` 或套件原始碼位置
3. ⚠️ 逐步推演錯誤路徑證明觸及不到
4. ✅ **實際執行現有測試／型別檢查／唯讀探測腳本或聚焦 E2E** 拿回真實輸出證明不會爆（嚴守專案 DB 安全規範，不可觸碰非測試環境）

## 回報格式

1. **隱性爆炸半徑清單**（依風險高低排序：影響對象、為什麼 `grep` 漏掉、具體檔案與行號）
2. **關鍵安全假設實證結果**（列出驗證了哪幾個關鍵假設、跑了什麼指令、拿到什麼輸出、停在哪一層實證）
3. **未覆蓋盲點與建議補測／防護**（若有環境限制無法實測，明確寫出未驗證範圍）
