# Troy Eval — 雙盲 A/B 評測工作流程

以可控、雙盲（Double-Blind）的方式，對照「對照組（修改前／基準）」與「實驗組（修改後／新版）」在同一真實任務上的實際行為與產出品質，避免僅憑主觀印象或單次試跑產生確認偏誤。

> 若存在 `~/.agents/CONTEXT.md`，先讀取並遵守其語言與表達規範。核心機制參考 `pstack` 的 `eval` 規範：防觀察者效應、隱藏評分表、只採信實際操作軌跡與產出證據。

## 嚴格禁令（Blinding Non-Negotiables）

1. **禁止考試字眼洩漏**：提供給參賽代理的工作目錄名稱、檔案名稱、Prompt 內容中，**嚴禁出現**以下字眼（中英文皆然）：
   `eval`、`test`（指考試／評測語意時）、`judge`、`experiment`、`rubric`、`score`、`compare`、`benchmark`、`candidate`、`arena`、`A/B`、`對照組`、`實驗組`。
2. **自然任務包裝**：Prompt 必須像日常真實工作指令（例如：「請依工作目錄內的規範處理這份變更／需求並回報結果」），不得要求參賽者「展示你如何遵守某條新規則」。
3. **評分表隔離**：評分標準（Rubric）只能給最後的裁判看，參賽代理全程不可讀取。
4. **不信自我回報**：評分一律依據實際產出、修改後的程式碼、實跑指令輸出與真實執行軌跡（Transcript 工具呼叫順序），不採信參賽者口頭宣稱「我已確認通過」。

## 執行流程

### Step 1：定題與撰寫隱藏評分表

1. 明確定義變數：
   - **對照組（Baseline）**：例如修改前的規則檔（如 `dev` 分支版本）或無該 skill 的預設環境。
   - **實驗組（Treatment）**：修改後的新版規則／skill 檔。
   - **固定控制變數**：兩組使用相同模型與相同的自然工作輸入。
2. 撰寫 **3~6 條具體、可客觀判定的評分標準（Rubric）**，存於暫存筆記或對話內部狀態，**不寫進參賽者可見目錄**。

### Step 2：建立隔離且去識別化的工作環境

於對話專屬暫存目錄（或系統暫存資料夾，避免污染專案 git 工作區）建立兩份獨立工作夾（命名須中性，例如 `work-alpha/`、`work-beta/`）：

- 放入**完全相同**的任務材料、相關程式碼與依賴（需跑測試或 Git 歷史查證時，一併建立隔離的迷你 Git 倉或環境）。
- 僅在各自對應位置放入「對照組版本」與「實驗組版本」的規則／skill 檔。
- 檢查所有檔名、目錄名與文字內容，確認無違反上述 Blinding 禁令。

### Step 3：平行派出兩組獨立代理

使用**相同模型**，平行啟動兩個獨立 subagent（依當前 AI 工具提供之背景代理機制）：

- 兩份 Prompt **除了各自讀取的工作目錄路徑不同外，其餘字句 100% 相同**。
- 明確限制每個代理只能讀取與操作各自被指派的隔離目錄（避免讀到另一組或外部真實專案）。
- 收集兩組完整產出；若評測目標涉及「步驟順序」（如先紅燈重現再改程式、先補測試再重構），**務必從代理的執行日誌／Transcript 提取真實工具呼叫順序**一併交給裁判。

### Step 4：匿名盲審（Blinded Judge）

1. **匿名遮罩**：隨機決定將兩組產出對應為「方案 X」與「方案 Y」（記錄對應表於最後解盲使用，裁判不可得知）。
2. **獨立裁判**：啟動第三個獨立代理擔任裁判（優先選用與參賽者不同模型家族，或高推理模型），僅提供：
   - 任務原始材料
   - Step 1 的隱藏評分表（Rubric）
   - 遮罩後的「方案 X」與「方案 Y」完整產出（及必要之真實執行時間軸）
3. 要求裁判逐條依證據判定 Pass / Partial / Fail，並給出具體差異與行號理由。

### Step 5：解盲、覆核與清理

1. 將「方案 X / Y」解盲還原為「改前（Baseline）vs 改後（Treatment）」。
2. 人工／主代理覆核裁判判決是否與實際產出一致。
3. 輸出精簡對照報告（預設呈現於對話或 Artifact，不污染專案 repo）：

| 評分項目 | 改前（Baseline） | 改後（Treatment） | 關鍵證據差異 |
|---|---|---|---|
| <標準 1> | ❌ / ✅ | ✅ / ❌ | <具體抓到或漏掉的點> |

4. 若實驗組未達預期或出現副作用（例如新規則稀釋既有敏感度），直接指出需微調的條文；**完成後務必刪除暫存評測資料夾**。
